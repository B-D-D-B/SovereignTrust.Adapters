## Ownership and target behavior

1. The ST plan or caller supplies the **fully formatted provider-native** `Config.Prompt` object, including `model` and any provider-supported optional JSON fields. Registration owns the profile key → model/route/credential binding. The provider decides whether the selected model supports specific `n`, `size`, `output_format`, quality, background, image count or other native options. The adapter does not insert defaults, compose prompt text, maintain an allowed native-field list, or duplicate provider option policy. A body with different options must reach REST unchanged in value and JSON shape.
2. Keep a small adapter trust boundary: require object-shaped `Config` with exactly `Profile` and `Prompt`, object-shaped `Profile` with exactly string `Key`, a configured unique profile/route/resource binding, a native object `Prompt` with string `model` exactly equal to the selected registered model, and a bounded JSON serialization. Reject unknown `Config` controls before cloning so callers cannot set URI, method, headers, tokens, body, query, file/form or REST result controls. Preserve raw array types during checks. `Config.Profile` remains the v2 image selector; legacy `Config.ModelKey` is retained for Responses text only. `SendMessageOriginal` does not gain image dispatch.
3. Keep transport and route guards: fixed HTTPS `api.openai.com:443` origin, no URL user-info/query/fragment, registered API-kind/path relationship for `/v1/images/generations` and `/v1/images/edits`, `AuthMode=ApiKey`, nonblank hydrated credential, exact jacket index/reference checks, server-chosen POST/host/URI/bearer header/JSON content type/`SkipBearerToken`, cloned Plan and failure propagation. Route API kinds remain a narrow allowlist because this is an OpenAI Images adapter, not arbitrary URL dispatch. A new endpoint kind needs its own reviewed transport mapping. Keep the 1 MiB serialized request bound as a local resource guard, measuring UTF-8 bytes using the same depth-100, noncompressed serialization as REST. Treat serialization failure or depth truncation as rejection before dispatch; do not measure the old compressed depth-12 representation.
4. Keep `stream:true` rejected (and malformed `stream` rejected) until REST has an event-stream result contract; `stream:false` or omission may pass. This is a transport compatibility guard, not a provider option default. Preserve a narrow safety check for edit `images` references **when present**: JSON array of reference objects with HTTPS absolute `image_url` free of credentials/fragment/control characters or bounded nonblank `file_id`; allow more than one reference and do not pin the provider's exact count or require `images` for every future model. If this narrow check rejects a newly supported provider reference form, stop and review that trust-boundary change rather than silently accepting local-file/unsafe URLs. Do not add a recursive provider-payload validator.
5. Retain v1 and v2 Responses text behavior, normalized text result, `HandleMessage`, and current image parsed REST Result. The generic provider-native v2 Responses send is a separate possible phase: it would change the existing text input/output contract and needs its own scope, plan and evidence. It is not a prerequisite for this image simplification.
