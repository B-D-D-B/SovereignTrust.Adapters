### Contract and supported boundary

The adapter neither formats instructions nor calls a formatter/validator, inserts defaults, rewrites native fields, pins profile names/model IDs/options, nor validates provider-specific reference forms. The trusted registration binds the arbitrary profile key to exactly one model, route, address, resource and authentication mode. Route `ApiKind`, not key spelling, determines HTTP protocol. The configured profile model must exactly match `Prompt.model`.
- AzureFoundry uses the existing `Signal` jacket and `Resolve-PathFromDictionary -Dictionary $this.Signal` to resolve `%.@.Profiles`, `%.@.Routes`, `%.@.Resource` and selected indexed address/credential. Reject missing, duplicate or mismatched profile, route and resource references. For Images generation/edit, clone the Plan only after rejecting every caller REST control in `Config`, set `Body` to the same native `Prompt` object, bind registered HTTPS URI/host and header from the selected resource, use `POST` through `Invoke-MappedAdapter -Adapter 'Condenser.Rest'`, and forward its parsed `Response` value. These are three adapter implementations, with two distinct AzureFoundry API kinds. Adapters validate closed route-specific fields and transport them, with only unavoidable protocol encoding explicitly identified. They do not rewrite prompt text, run a formatter phase or read a prompt template. This plan stops at a bounded, opaque transport receipt. Parsing a provider image, choosing a resulting URL/base64 payload, persisting it, vision classification, and `HandleMessage` are separate work covered by the [image-output design](./Intelligence-Image-Output-Integration-Plan.md) and its blocked prerequisites.

An image send returns a typed opaque receipt, never manufactured `choices[0].message.content`.

## Input contract and activity decision

“Send side” means request validation and transport here. `SendMessage` is the mapped activity for text and image profiles. `Config.ModelKey` selects a profile, whose `RouteKey` selects the configured API kind, address and resource; the adapter validates this binding and adds the selected model and authentication mechanically. Legacy text sends retain their current response normalization. Image helpers return the receipt below. `HandleMessage` and image response interpretation are deferred.

For this send campaign, the newer user boundary supersedes the older multi-provider proposal's `GenerateImage` parsed `{kind:'image'}` result and `Config.FormattedPrompt` input: use only `Config.Prompt` and the opaque receipt below. Preserve the old proposal as history. Document the profile-dependent `SendMessage` result variants in the Foundation catalog/result contract and update callers that select image profiles. The receipt's `Kind:"ImageSendReceipt"` discriminant distinguishes it from legacy text JSON strings. The separate image-output design must later consume the receipt through an explicitly reviewed image-response step before materialization/evaluation. This plan neither implements that step nor prescribes a change to `HandleMessage`.

For an image send, `Plan.Config` has exactly `ModelKey` and `Prompt`; `ModelKey` is explicitly `ImageGenerate` or `ImageEdit` and selects a profile in the resolved jacket. The selected profile fixes API kind, model, route, credentials and allowed operation. An omitted key continues to select the configured text default. Reject mismatched profile/route/prompt shape before transport; neither the request payload nor caller can override model, address or credentials.

`Config.Prompt` is an **already formatted provider-native request payload** supplied by trusted ST content or another caller. Each selected API kind has its own closed allowed fields and types; there is no universal image Prompt schema. For OpenAI Images generation, it contains final `prompt`, `n:1`, `size:"1024x1024"`, `output_format:"png"`; for OpenAI Images edit, it additionally contains `images` with exactly one `{image_url}` HTTPS reference or `{file_id}` reference, as supported by the [official edit JSON API](https://developers.openai.com/api/reference/resources/images/methods/edit). The direct OpenAI pilot accepts these JSON forms only. `model`, endpoint, headers, auth and executable instructions are forbidden in Prompt and come only from the selected profile/route/resource. Foundry OpenAI also documents [JSON image references](https://learn.microsoft.com/en-us/azure/foundry/reference/rest/images-create-image-edit-multipart-images-create-image-edit-json), but its exact deployed route/field support remains a prerequisite. Foundry BFL's [FLUX.2 guide](https://learn.microsoft.com/en-us/azure/foundry/foundry-models/how-to/use-foundry-models-flux) shows bare base64 `input_image`; URL acceptance is unproven, so the upstream producer must provide the supported base64 payload or an explicitly reviewed mechanical local-file encoding step must be established before that edit route. CodexCLI requires a separately proven artifact command and its own closed preformatted input. Selected route limits and reference lifecycles must be verified before live send.

The adapter validates and serializes the selected provider-native Prompt without changing its instruction text or constructing prompt content. It adds only the configured model/auth/route fields needed for transport. For BFL, an upstream accepted formatter may create this value; **the adapter does not call that formatter**. The existing [multi-provider plan](./Intelligence-AzureFoundry-MultiProvider-Plan.md) proposed `FormattedPrompt`; image callers migrate prospectively to `Config.Prompt` while existing text `SendMessage` callers remain unchanged. Image profiles reject `FormattedPrompt`, raw legacy `Config.Content` and a parsed image result.

The image send result is a versioned opaque receipt, **never an image interpretation**. Common required fields are `SchemaVersion:1`, `Kind:"ImageSendReceipt"`, `Slot`, `ModelKey`, `RouteKey`, `Transport:"Http"|"Process"`, `CaptureId` (fresh run-scoped identifier), and `CaptureRoot` (canonical absolute path under the jacket's approved `ImageCaptureRoot`). The `Http` variant has exactly `StatusCode:200`, `ContentType:"application/json"` (optional UTF-8 charset), `RawBodyPath`, `RawBodyLength` (integer 1 through 64 MiB), and `RawBodySha256`; it has no process fields. The initial request is explicitly nonstreaming. Treat 201/202, a redirect, empty body, non-JSON content type, oversized body or unfinished stream as unsupported/failure, not completed-image success. The `Process` variant has exactly `ExitCode:0`, `OutputDirectory`, `StdoutPath`, `StdoutLength`, `StdoutSha256`, `StderrPath`, `StderrLength`, and `StderrSha256`, with each capture at most 1 MiB (zero-length stdout/stderr allowed); it has no HTTP fields. Require the child to exit, both capture files to close and digest checks to pass. The receipt does not say whether Codex produced an image; that belongs to the later response/artifact consumer. A selected model that legitimately returns another status or streaming protocol needs a revised receipt contract before use.

The adapter creates a fresh exclusive `ImageCaptureRoot/<CaptureId>` directory with no preexisting target; the receipt's `CaptureRoot` is that exact canonical per-call directory. It writes bounded body/stdio files there, flushes them and computes final digest/length before returning a success receipt. The sender owns cleanup until it returns the receipt. A transport, cancellation, timeout or write/digest failure before return removes only its newly created capture and yields a failed Signal with no success receipt. Before a live send starts, a separately reviewed run-scoped owner/finalizer must already be responsible for any returned capture; a response consumer may explicitly accept ownership from that owner later. Returning success ends sender ownership: later consumer failure cannot retroactively change the send Signal or cause the sender to delete an accepted capture. The run owner/finalizer handles unaccepted receipts, consumer failure and interruption from durable ownership receipts; no current ST-Test.ps1 finalizer is assumed. Until that ownership/consumer contract and configured root exist, live sends remain blocked. Offline transport tests use a test-owned capture root, verify retention on successful return and deletion on send failure, and always clean their own captures in test teardown. They do not implement image response handling. Do not log credentials, prompt text, raw body, reference bytes or tokenized URL. No public runner or ST test result uses this receipt as an image success oracle.
