# Intelligence.AzureFoundry multi-provider implementation plan

**Purpose and scope.** Proposed future implementation for registered function F-FOUNDRY-MULTI-PLAN-01. This document is a design, not evidence of runtime behavior or authorization to deploy. Preserve existing `OpenAIResponses` slots and their `SendMessage`/`SendMessageOriginal` text result. Add BFL FLUX.2 [pro] and [flex] only through the provider-specific API, with an ST prompt-format phase before ST-managed BFL provider calls. No arbitrary handler or PowerShell function name is read from configuration.

## Evidence and architectural choice

- Current [Foundry module](../Src/Intelligence/AzureFoundry/PowerShell/Intelligence_AzureFoundry.psm1) dispatches both message activities to one Responses helper after slot-level `ApiKind` validation. The [helper](../Src/Intelligence/AzureFoundry/PowerShell/Invoke-AzureFoundryOpenAIResponses.ps1) accepts one `Addresses` URL and one hydrated `Resource`, resolves `Config.ModelKey` against profiles, builds Responses text/image input, and returns a JSON string containing `choices[0].message.content` from assistant text. The [README](../Src/Intelligence/AzureFoundry/README.md) documents this supported shape.
- [MappedIntelligenceAdapter](../../SovereignTrust.Foundation/Src/PowerShell/Classes/Adapters/MappedIntelligenceAdapter.ps1) currently allows only `SendMessage`, `SendMessageOriginal`, and `HandleMessage`; a new image activity requires an explicit Foundation contract change. [Resolve-ConductorAdapters](../../SovereignTrust.Foundation/Src/PowerShell/Utilities/Adapters/Resolve-ConductorAdapters.ps1) can use lazy registration, and [Resolve-RegisteredAdapter](../../SovereignTrust.Foundation/Src/PowerShell/Utilities/Adapters/Resolve-RegisteredAdapter.ps1) then resolves the jacket and module on first use. With lazy loading enabled, declaring many mapped adapters does **not** imply eager imports. Without it, the loader resolves each jacket during startup. Multiple adapters still add catalog, configuration, versioning and operational surface even when load cost is deferred. Verify deployment's `UseLazyLoading` setting before claiming a performance benefit.
- Microsoft's current [FLUX deployment and API guide](https://learn.microsoft.com/en-us/azure/foundry/foundry-models/how-to/use-foundry-models-flux) names model IDs `FLUX.2-pro` and `FLUX.2-flex`, but endpoint paths `flux-2-pro` and `flux-2-flex`: `POST https://<resource>.api.cognitive.microsoft.com/providers/blackforestlabs/v1/<model-path>?api-version=preview`. It shows `Authorization: Bearer <API_KEY or Entra token>`, body `model` plus `prompt`, optional base64 reference fields `input_image`, `input_image_2`, etc., and an image URL **or** base64 image response. It limits pro to eight and flex to ten references. The guide's Image API route applies to FLUX.1 models, so do not use it for FLUX.2. Recheck preview shape at implementation time.

**Recommendation.** Keep one mapped `Intelligence_AzureFoundry` class and existing slot name. Use a small fixed dispatch map from validated `ApiKind` plus activity to two private, explicit handlers: `OpenAIResponses` for text and `BlackForestLabsFlux2` for image generation/editing. A switch is sufficient for two kinds; a private registry of fixed function references becomes useful only if the handler list grows. Several class methods are possible but would couple transport-specific request and result parsing to the mapped entry point; keep the class responsible for selection and Signal forwarding. The one-adapter approach reuses slot hydration, profile selection and common guardrails while allowing separate API request builders. Do not turn config into executable handler names or a universal field mapper.

One mapped adapter per provider is reasonable if providers need separate ownership, release cadence, security boundary or incompatible activity/result contracts, or if measured startup/module cost warrants it. It simplifies each class and permits distinct deployment lifecycles, but increases module/manifest/catalog/jacket maintenance. Lazy loading weakens the assumed startup-cost argument for consolidation. If the common class accumulates more than a few unrelated API kinds, revisit this split with measurements and concrete contracts.

### Adapter load costs and tradeoffs

| Choice | Benefit | Cost / limitation |
| --- | --- | --- |
| One class, private fixed functions (recommended) | One slot and release; provider request/result builders remain isolated and testable | Resolving that slot loads both handler definitions; one release affects both APIs |
| One class, internal methods | Fewest files and direct state access | More transport and parsing code inside the entry class; no inherent startup saving over equivalent private functions |
| Separate provider adapters | Independent releases and only the selected provider module need resolve in lazy mode | Additional manifests, jackets, registrations and maintenance; eager mode resolves every declared jacket |

Actual source operations, not measured milliseconds: every jacket incurs metadata lookup and mapped-slot registration. Lazy registration stores a handle; first use takes its lock, resolves the dependency graph/module, creates the instance, merges and hydrates settings, and calls `Construct`; subsequent use returns the stored instance. Eager mode does that resolution during startup. [Resolve-AdapterFromJacket](../../SovereignTrust.Foundation/Src/PowerShell/Utilities/Adapters/Resolve-AdaptersFromJacket.ps1) calls [Resolve-DependencyModuleFromGraph](../../SovereignTrust.Foundation/Src/PowerShell/Utilities/Adapters/Resolve-DependencyModuleFromGraph.ps1), whose ordinary provider path reaches [Resolve-ModuleFromAdapter](../../SovereignTrust.Foundation/Src/PowerShell/Utilities/Adapters/Condenser/Fab/Resolve-ModuleFromAdapter.ps1) and `Import-Module -Force`; do not assume a global module cache removes repeated jacket-resolution costs. Consolidation can reduce this work when several providers are used, while separate lazy adapters can avoid loading unused provider code. No elapsed-time or memory measurements were collected; neither architecture has a demonstrated performance win.

## Proposed jacket and route contract

This is an **illustrative version-2 AzureFoundry jacket and structural schema**, not a committed runtime or global adapter schema. All keys are case-sensitive; examples use placeholders, never actual secrets. Each `Routes` entry has its own `Address` and a `ResourceKey` pointing to one object in the `Resource` collection; profiles reference routes by `RouteKey`. Pro and flex intentionally share one hydrated `Resource.Credentials` string via the same key. `Resource` is an expandable object collection, but this AzureFoundry revision defines only `Key` and required `Credentials`; future noncredential fields need adapter-specific schema decisions and are rejected until defined. The selected route's `AuthMode` determines how its referenced `.Credentials` string is sent. Other adapters use `Resource` for different kinds of values, so this proposal does not reinterpret their jackets or impose a universal secret contract. Singular `Resource` follows the existing jacket name and requested convention; plural `Resources` might read more naturally for a collection but would create an unnecessary migration and mixed-name ambiguity. Route `ApiKind` is a closed enum, not a function name. A route's model ID and URL path are separately validated against the fixed FLUX.2 table.

```json
{
  "Name": "Foundry",
  "VirtualPath": "SovereignTrust.Adapters.Intelligence.AzureFoundry.Foundry.Persistent.Run",
  "IsMapped": true,
  "SchemaVersion": 2,
  "Resource": [
    { "Key": "openai-east", "Credentials": "[Storage.Secrets.Read.foundry-openai-key|]" },
    { "Key": "bfl-east", "Credentials": "[Storage.Secrets.Read.foundry-bfl-key|]" }
  ],
  "Routes": [
    { "Key": "responses", "ApiKind": "OpenAIResponses", "Address": "https://YOUR_OPENAI_RESOURCE.openai.azure.com/openai/v1/responses", "ResourceKey": "openai-east", "AuthMode": "ApiKey" },
    { "Key": "flux-pro", "ApiKind": "BlackForestLabsFlux2", "Address": "https://YOUR_FOUNDRY_RESOURCE.api.cognitive.microsoft.com/providers/blackforestlabs/v1/flux-2-pro?api-version=preview", "ResourceKey": "bfl-east", "AuthMode": "BearerApiKey" },
    { "Key": "flux-flex", "ApiKind": "BlackForestLabsFlux2", "Address": "https://YOUR_FOUNDRY_RESOURCE.api.cognitive.microsoft.com/providers/blackforestlabs/v1/flux-2-flex?api-version=preview", "ResourceKey": "bfl-east", "AuthMode": "BearerApiKey" }
  ],
  "Profiles": [
    { "Key": "Worker-Medium", "IsDefault": true, "RouteKey": "responses", "Model": "YOUR_RESPONSES_DEPLOYMENT", "ReasoningEffort": "medium" },
    { "Key": "Image-Pro", "IsDefault": false, "RouteKey": "flux-pro", "Model": "FLUX.2-pro" },
    { "Key": "Image-Flex", "IsDefault": false, "RouteKey": "flux-flex", "Model": "FLUX.2-flex" }
  ]
}
```

Structural rules: require `SchemaVersion=2`, an explicit Boolean `IsDefault` on every `Profiles[]` entry with exactly one `true` globally per mapped slot, nonblank unique ordinal `Profiles.Key`, `Routes.Key`, and `Resource.Key`, and exact ordinal `Profiles.RouteKey`/`Routes.ResourceKey` references. Reject missing or duplicate profile keys, absent/non-Boolean `IsDefault`, zero or multiple `true` defaults, missing, blank, unused or duplicate resource keys, orphan routes without a profile, unknown references, and mixed or ambiguous version-1/version-2 fields. An intentionally shared resource key is valid when multiple routes explicitly reference it; equality of two `Credentials` strings does not imply sharing or select a route. For AzureFoundry authentication, require each selected `Resource.Credentials` to be a hydrated nonblank string before use; a hydration token left unresolved fails before HTTP. Permit `ApiKey`/`Entra` on Responses and `BearerApiKey`/`BearerEntra` on BFL, each with its documented header, and reject every other combination. Reject top-level `DefaultModelKey` in version 2 and version-2 profile objects containing `ModelKey` (including mixed `Key` plus `ModelKey`), `Resource` fields other than `Key` and `Credentials` (including old `Value`), and unknown or duplicate JSON property names, unsupported URL schemes/hosts/paths, and extraneous profile fields inappropriate to its API kind (for example `ReasoningEffort` on FLUX). A JSON parser that collapses duplicate object properties is insufficient. During preflight identify the existing raw-JSON ingress and prove duplicate rejection there before conversion; the adapter receives a hydrated object and cannot reconstruct discarded duplicate keys. If that boundary cannot enforce this for version 2 within owned scope, stop dependent version-2 work and review the required ingress change. Validate each route's `Address` and `AuthMode` independently against its API kind and selected model's fixed path; never inherit either from a sibling route sharing a resource. Do not let a plan supply addresses, headers, resources, model IDs or handler names. Redact resource credentials, provider bodies, image data and tokenized URLs from Signal/log errors.

`Config.ModelKey` remains the request selector for compatibility: it matches version-2 `Profiles[].Key`; unknown keys fail before HTTP. When omitted, select the sole profile with `IsDefault=true` for the mapped slot. If that global default has an API kind incompatible with the requested activity, fail before HTTP and require an explicit `Config.ModelKey`; do not silently choose another profile or invent per-activity defaults. No request-plan field migration is proposed. `Config.Model` remains unsupported. A selected profile fixes activity, API kind, route address, resource reference, authentication, and model. `SendMessage`/`SendMessageOriginal` may select only `OpenAIResponses`; new `GenerateImage` may select only `BlackForestLabsFlux2`. This prevents an image response from appearing as assistant text. `HandleMessage` retains its current selection/format behavior. If product callers require image editing as a separate named activity, decide that in the Foundation contract review before implementation; this plan uses one `GenerateImage` activity with optional references.

### ST prompt-format phase before the provider call

For ST-managed FLUX requests, select the profile by explicit `Config.ModelKey` or the sole `IsDefault` profile, then follow `Profile.RouteKey` to the route. ST-owned, reviewed plan content maps the resolved `ProfileKey` to a format phase compatible with that route's fixed `ApiKind`; pro and flex may share one BFL phase, while a later profile may use a different trusted template. An unmapped or incompatible profile/phase fails before HTTP. The request must not supply an arbitrary plan path or executable function name. ST invokes its standalone provider-specific phase **before** the adapter call and is the sole composer of new BFL prompt content. The phase returns a typed `FormattedPrompt` containing the final BFL `prompt` text and ordered image references; the adapter validates and serializes it, without rebuilding text, system, or media formatting.

The proposed narrow selection bridge is a read-only mapped `ResolvePromptProfile` activity on the same AzureFoundry slot, added to Foundation's allowed activities. It takes optional `Config.ModelKey` and required `Config.TargetActivity`, uses the same internal selector/activity-compatibility check as provider invocation, and returns only `{Slot, TargetActivity, ProfileKey, RouteKey, ApiKind, FormatKind}`. It performs no provider HTTP or prompt formatting; first-use slot construction/hydration may still occur. `TargetActivity` is validated data, not an executable handler. ST receives no jacket resource object or `Resource.Credentials`. The formatter's selection fields are consistency data, never an authorization token: the adapter reselects from its own current jacket and compares them before transport. Existing [Invoke-PlanPhase](../../SovereignTrust.Foundation/Src/PowerShell/Utilities/Adapters/Condenser/Plan/Invoke-PlanPhase.ps1) executes a phase and exports named results, but the complete selection-to-format-to-provider handoff remains a pre-implementation contract check. Use the ST integration content paths named below; if the handoff cannot preserve slot, activity, selected profile and typed output without exposing credentials, stop dependent execution.

The portable BFL phase emits `Config.FormattedPrompt = {schemaVersion:1, formatKind:'BlackForestLabsFlux2', profileKey, selection:{Slot,TargetActivity,RouteKey,ApiKind}, content:{prompt,media}}`. `content.prompt` is the final nonblank text and `content.media` is an ordered array of typed image references using exactly one authorized local `MediaPath` or base64 image data `MediaUrl` per item. The phase contains no project-specific secret, absolute path or credential. It must not fetch remote media, set endpoint/headers/auth, or serialize the BFL wire body. On `GenerateImage`, the adapter reselects the profile, checks profile/route/activity/format consistency and applies the shared envelope validator described below; then it enforces its own model, address, auth, image count/bytes/path/URL and transport limits and serializes the validated content into `model`, `prompt`, `input_image` fields. It does not join, rewrite or invent prompt text. A forged but self-consistent selection cannot bypass these checks. Legacy Responses callers keep raw `Config.Prompt` and the existing result. New BFL calls require `Config.FormattedPrompt` from a compatible ST format plan; direct callers must invoke that reusable plan or another reviewed producer of the same contract before calling the adapter. No raw BFL prompt builder is added inside the adapter.

### Small shared formatted-content validator

Foundation is the proposed owner of one exported `Assert-STFormattedPrompt` utility because Foundry, OpenAI and CodexCLI modules already import Foundation. It validates the versioned envelope once and uses a fixed `formatKind` rule table, not a pluggable function registry. The Responses rule is shared by Foundry Responses and the native OpenAI adapter when that adapter accepts formatted content; the FLUX.2 rule requires `prompt` plus bounded image references; CodexCLI needs its own text/media rule when its typed path is introduced. This campaign wires the BFL rule and checks the Responses rule without changing CodexCLI's existing raw behavior. Revalidate this dependency and export location before the Foundation change; if unavailable, resolve ownership with Foundation rather than copy the validator into provider modules.

```text
Assert-STFormattedPrompt(envelope, expectedKind, selectedProfile):
  require schemaVersion == 1, formatKind == expectedKind, profileKey == selectedProfile.Key
  reject unknown envelope/selection/content fields and invalid field types
  check selection slot/activity/route/API against the adapter's reselected profile
  switch expectedKind (fixed):
    OpenAIResponses -> structured system/text/media rule (shared by OpenAI and Foundry)
    BlackForestLabsFlux2 -> nonblank prompt; bounded image-reference list; no system role
    CodexCLI -> distinct text/media rule only when its typed contract is adopted
  return validated typed content; never compose the prompt or choose credentials
```

The shared validator enforces format version/kind, profile and route identity, allowed fields/types, and bounded media structure. The adapter owns selected model, endpoint/auth, exact media count and decoded byte/path/URL safety, transport and response checks. Strict plan authoring, pinned hashes and integration fixtures reduce producer mistakes but do not cover dynamic hydrated inputs, later plan/config drift or direct callers, so the minimal runtime guards remain. A future trust optimization needs measured evidence and a narrower reviewed contract; it cannot remove route/auth or malformed-payload checks merely because a test passed.

## Migration and input/output semantics

1. Preserve the version-1 jacket contract (`ApiKind=OpenAIResponses`, `Addresses` with exactly one URL, `Resource` with exactly one hydrated credential, optional `AuthenticationMode`, `Profiles`, `DefaultModelKey`) through a versioned compatibility parser. Preserve the current parser's accepted scalar-string and singleton-string-array forms for `Addresses` and `Resource`, and its `ApiKey` default when `AuthenticationMode` is absent. Treat absent `SchemaVersion` as version 1 when the existing legacy validator accepts the jacket and no version-2 fields are present; do not narrow legacy acceptance to the array example. Convert it **in memory** to one Responses route (`Routes[0].Key`, `Address`, `ResourceKey`, `ApiKind`, `AuthMode`) and one keyed resource (`Resource[0].Key`/`Credentials`); normalize each legacy `Profiles[].ModelKey` to `Profiles[].Key` in memory, set `IsDefault=true` only for the profile matching legacy `DefaultModelKey` (false for the others), and bind all legacy profiles to that route. Do not rewrite deployed jackets or change existing slot names. Version 2 requires keyed `Resource` objects and `Routes`; reject mixed version-1/version-2 fields instead of silently preferring one, including top-level `Addresses`, `ApiKind`, `AuthenticationMode` or `DefaultModelKey` in a version-2 jacket. Keep existing Responses payload and `choices[0].message.content` result unchanged; verify with current fixtures.
2. Preserve current direct and legacy Responses `Config.Prompt.System`, `Texts`, `Media`, `Config.Content`, `MediaPath` and `MediaUrl` behavior, including the system role and ordered text/image parts. New BFL ST content is composed only in the standalone format plan: it rejects nonblank `System`, builds one final image prompt, and emits ordered image references. The adapter rejects a raw BFL `Config.Prompt`, `Config.Content`, or mixed raw/formatted input. No generic `PromptMap` or provider prompt builder is added to the adapter.
3. `GenerateImage` accepts `Config.ModelKey`, required `Config.FormattedPrompt`, and a closed `Config.Image` option set verified against the official FLUX.2 API (initially `Width`, `Height`, `OutputFormat`, `Seed`; add `Guidance`/`Steps` only after model-specific validation). Limit references to eight for pro and ten for flex, validate image format/size and total request size before transport, and reject conflicting/unknown options. The adapter serializes the already formatted `prompt` and validated image references as documented `model`, `prompt`, `num_images=1`, and numbered bare-base64 `input_image` fields; it sends no Responses `reasoning` or `max_output_tokens` fields and performs no prompt composition.
4. `GenerateImage` returns a successful Signal with a **new versioned image result object**, e.g. `{ "schemaVersion": 1, "kind": "image", "modelKey": "Image-Pro", "images": [{ "source": "url", "url": "https://..." }] }` or `{ "schemaVersion": 1, "kind": "image", "modelKey": "Image-Pro", "images": [{ "source": "base64", "mimeType": "image/jpeg", "data": "..." }] }`. Preserve the provider's image material as image data, not `choices[0].message.content`. Require one image with a valid source and safe bounds; reject malformed, empty, ambiguous or extra output until contract evidence warrants them. Provider documentation describes URL/base64 alternatives but does not pin a stable response field name in the guide; implementation must obtain a current official schema or deployment fixture and bind exact parser fields before execution. Consumers must explicitly handle either source and its lifetime/access requirements; do not log or coerce image bytes to text. Failed calls return failed Signal without Result, with sanitized diagnostics.
