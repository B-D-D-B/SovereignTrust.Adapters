# Intelligence.OpenAI implementation plan

**Purpose and boundary.** F-OPENAI-PLAN-01 proposes a native OpenAI API adapter for the existing mapped intelligence interface. This is a future execution plan, not an implementation or runtime acceptance claim. The implementation campaign is one bounded function, subject to an independent D1–D8 READY for this exact revision before mutation and an independent R1–R8 review of its frozen aggregate result. No deployment, catalog publication, commit, or push is part of this planning cycle.

## Implementation contract

The following bounded first-release choices are fixed for implementation and must be documented in the README and tests. The user confirmed the API key is in Resource, as in Foundry. Deployment model IDs and account access are live-preflight inputs, not reasons to defer offline work. A later change to these semantics requires affected readiness review.

1. Name the class/module `Intelligence_OpenAI` under `Src/Intelligence/OpenAI/PowerShell/`, with a distinct module GUID and exported `Resolve-Intelligence_OpenAI`. Use one `OpenAIResponses` API kind. Implement `SendMessage` and `SendMessageOriginal` with the same normalized result, matching current Foundry behavior; neither exposes a raw provider envelope. Implement `HandleMessage` using the existing `Path` lookup and optional `Format` dispatch: preserve native selected values, success without Result when the selected Signal lacks one, and failed Signal/no Result for lookup/format failure. Reject unsupported activity/API kinds with a failed Signal.
2. Require exactly one `Addresses` entry whose parsed URI is HTTPS, host `api.openai.com`, port 443, absolute path `/v1/responses`, with no userinfo, query or fragment. No omitted-address default or custom host in this release. Require exactly one nonempty hydrated `Resource` API key per slot, as explicitly confirmed by the user. Send `Authorization: Bearer <key>` and `Content-Type: application/json`; no Azure authentication, token acquisition or deployment paths. Do not expose credentials in logs, Results, fixtures or committed files. Tests use dummy keys and intercept HTTP; production host validation is never relaxed for tests.
3. Require `DefaultModelKey` and nonempty `Profiles` with unique ordinal `ModelKey`, a nonempty native OpenAI model ID `Model`, optional `ReasoningEffort` and positive integer `MaxOutputTokens`. `Config.ModelKey` selects a profile; reject unknown keys and `Config.Model` override before HTTP. Omit reasoning/output-budget fields unless configured. Accept effort names from the current Responses schema and document that support depends on the selected model; provider incompatibility fails normally. Omit `MaxInputTokens` from this adapter contract. Validate deployed model/effort/image support against official documentation before any live call; no model hardcoded in adapter source. An authorized live smoke request must use an explicit bounded MaxOutputTokens.
4. Support `Config.Prompt.System`, ordered `Config.Prompt.Texts`, and `Config.Prompt.Media` with Foundry media fields `MediaType`, `MediaPath` or `MediaUrl`, and `Detail`. Use `Config.Content` only when no structured Prompt is supplied; reject simultaneous forms and legacy top-level `Config.MediaPath`/`MediaUrl`. Build system/user Responses input with ordered text parts followed by media parts; require nonempty user text or media. Support local JPEG/PNG/WebP and non-animated GIF as data URLs; check signatures and reject animated GIF. Accept HTTPS image URLs with no userinfo; do not fetch remote files locally or claim their content/size was validated. Accept `low`, `high`, `auto`, default `auto`; model compatibility is checked at live preflight. Local raw files must each be at most 10 MiB, media count at most 10, and the complete UTF-8 serialized request at most 20 MiB (including encoded local images). Check length before reading local files and encoded aggregate before sending. Reject missing files, unsupported formats, both/neither source forms, invalid URL/detail/type, empty request and exceeded bounds before transport. No audio/file/tool/streaming behavior.
5. Use a private native HTTP helper in the new OpenAI module, preserving Foundry's Signal/profile/slot structure without calling `Condenser.Rest`. The existing REST core retries generic failures and logs raw provider error text; its unchanged behavior cannot meet this adapter contract. Make one synchronous `Invoke-WebRequest` POST with `MaximumRetryCount=0`, `MaximumRedirection=0`, `ConnectionTimeoutSeconds=30`, `OperationTimeoutSeconds=60`, `SkipHttpErrorCheck`, explicit JSON body/headers, and terminating error handling; suppress verbose/debug/progress output. Require PowerShell 7.4+ and verify these parameters exist at preflight. Do not inherit caller transport options or mutate the caller plan. Read status/content explicitly, accept only HTTP 2xx, parse JSON locally, and require status `completed` and at least one nonblank assistant `output_text`; reject any refusal, malformed/noncompleted/incomplete response, provider error or absent assistant text. Return a JSON string with `choices[0].message.role='assistant'` and ordered text joined with newline as `content`. On any failure return failed Signal/no Result with a fixed diagnostic category and optional numeric HTTP status; do not merge raw transport errors or attach exception/ErrorRecord/body/key/media to the Signal or emit them to output streams. No retries or redirects, including 401/429/timeout. No Foundation runtime edit is needed.
